# Философия разработки ИИ-команды

> Универсальные принципы, извлечённые из практики BeOnBoard (крупная инженерная платформа).  
> **Не обязательны целиком** в каждом новом проекте — возьми нужные § и роли по масштабу ([SETUP.md](SETUP.md) § «Масштаб команды»).

---

## 1. Зачем команда, а не один «супер-агент»

| Один чат на всё | Специализированные роли |
|-----------------|-------------------------|
| Размытые границы | Чёткий scope и эскалация |
| Контекст раздувается | L0/L1/L2 онбординг, новый чат на промпт |
| Дизайн = код = продажи | Designer / PTM / sales не смешиваются |
| Нет памяти между сессиями | `workers/` + sprint + tech-overview |

**Правило:** один исполнитель на задачу в `CURRENT_TASK.md`; остальные — WORKLOG «поддержка».

---

## 2. Память вне чата

Чаты Cursor **не переносятся**. Источники правды:

| Артефакт | Что хранит |
|----------|------------|
| `workers/<role>/WORKLOG.md` | Что делала роль |
| `workers/<role>/CURRENT_TASK.md` | Активная задача |
| `workers/sprint/CURRENT.md` | Спринт, очередь, журнал (top-60) |
| `{{TASKS_PATH}}/NNN_*.md` | ТЗ: scope, frozen, приёмка |
| `overview/` | Продукт для людей и sales |
| `{{TECH_OVERVIEW_PATH}}/` | Техника для разработки и scout |
| `CODE_CHANGE_BOARD.md` | Сигнал scout: код изменился |

---

## 3. Минимум промптов → максимум автономии

**Не дробить** работу на 30 микрошагов. **Крупные вертикальные срезы:**

- Плохо: P1 схема · P2 API · P3 UI · P4 тесты
- Хорошо: P1 recon+schema · P2 фича A end-to-end · P3 фича B · P4 GATE

| Параметр | Ориентир |
|----------|----------|
| Промптов на эпик | обычно **5–10**, максимум ~12 XL |
| 1 чат | **1 промпт N/M** |
| Self-review | отдельный слот, если diff **> ~400 строк** |
| Frozen в ТЗ | закон — не менять молча |

**Качество не торгуется.** Крупный промпт = агент дольше работает **сам**, но сдаёт код + тесты + артефакты.

---

## 4. Полная подсистема, не «MVP-заглушка»

Закрывать GATE только когда владелец видит **user-visible** результат на экране/в канале.

- Запрещено: «только API», «только настройки в JSON» без UI — как финал подсистемы.
- Разрешено: внутренние P без UI, если в runbook явно ведут к видимому P.

---

## 5. Reuse-first (код и UI)

Перед новым компонентом:

1. `code-map` / `tech-overview` / инвентарь виджетов
2. Существующие примитивы дизайн-системы
3. **NEW** — только с причиной в SESSION / Bon-spec / ТЗ

PTM и developer **не клонируют** picker/modal/list «под страницу».

---

## 6. Ясность языка (все роли)

- Сначала **смысл**, потом термины.
- UI и чат с владельцем — **без англо-жаргона** без перевода.
- ТЗ: цель человеческим языком; пути и API — блок «Техника».

Самопроверка: убери аббревиатуры — смысл остался?

---

## 7. Границы ролей (коротко)

| Зона | Кто владеет |
|------|-------------|
| Приоритеты, ТЗ, спринт | Team Lead |
| Код фич | Developer (или PTM после GATE) |
| Визуал / дизайн-бук | Designer |
| Система на сайте целиком | Product-TM |
| Идеи потока без пикселей | Outcome-UX |
| Ревью diff | Code Reviewer (report-only по умолчанию) |
| Приёмка | Tester |
| Безопасность | Cybersecurity → рекомендации → Developer |
| Инфра / CI | DevOps |
| overview/, tasks/ | Documentarian |
| tech-overview/ | Scout |
| КП, pitch | Sales |
| Посты | SMM |

**Эскалация рано** — не чинить чужую зону молча.

---

## 8. Токены без потери качества

| Рычаг | Действие |
|-------|----------|
| Префикс | Не читать AGENTS, tasks/README, журнал целиком |
| Сессии | Новый чат на каждый промпт |
| Файлы >300 строк | grep / Read с limit |
| Параллель | Не 3 developer на одно ТЗ |

Уровни: **L0** (промпт 2+) · **L1** (первый P) · **L2** (team-lead, scout).

---

## 9. Спринт и оркестратор

Владелец не держит 14 вкладок постоянно:

1. `Погнали спринт: <цель>` → Team Lead обновляет очередь
2. Открыть только `ready` (1–3 вкладки)
3. Агент: `running` → работа → `done` + журнал 1–3 строки

---

## 10. Честность в документации

- Продукт (`overview/`) = что **реально работает**
- Scout (`test_coverage`, `doc_coverage`) = отдельно от «красивого описания»
- Sales не обещает то, чего нет в product.md

---

## 11. Секреты и git

- Секреты **не** в `workers/` и **не** в чат
- Коммиты и push — **только по явной просьбе** владельца
- Минимальный diff; scope из ТЗ

---

*Адаптируй §4–5 под зрелость проекта. §1–3 и §8–9 — ядро для **крупных** команд; для маленького проекта хватит §2, §6, §11 и одной роли developer.*
